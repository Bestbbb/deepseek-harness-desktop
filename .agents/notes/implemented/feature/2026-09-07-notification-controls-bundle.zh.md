# Agent Note: 可选通知策略 Bundle

Status: implemented

[English](2026-09-07-notification-controls-bundle.md) | 中文

## 问题

插件市场需要一个无需修改 agent loop（智能体循环）即可改变桌面行为的任务行为示例。原生桌面已经发送通用的完成和失败通知；第二个发送方会重复送达，并模糊过滤与传输的包归属。

## 决策

可选的 [Notification Controls Bundle](../../../../packages/desktop/notification-controls/README.zh.md)提供独立、持久化的完成和失败开关，两者默认启用。现有原生提供方筛选出符合条件的实时顶层完成事件后，发出同步的 `desktop/task-notification` waterfall（瀑布式事件）。事件仅携带结果类型，不包含 Session 身份、任务文本或错误。没有策略时仍允许发送。

Bundle 注册可撤销的监听器，读取当前设置值，并通过 `next()` 委托或否决发送。策略抛出异常会阻止本次通知并记录通用警告，不会拒绝已提交的轮次。移除 Bundle 恢复默认原生行为；设置保留供重新安装使用。因此卸载不是静音操作，编辑器会说明该区别。

现有设置提供方负责校验和持久化。浏览器编辑器通过市场的键控操作 slot 提供入口，并根据 Host 观测确认受修订号约束的写入。市场为贡献内容提供独立的整行宽度，避免配置表单挤占包身份信息或移除控件。它不会添加市场专用的设置存储或乐观成功状态。经过审核的 tarball 携带 schema 依赖，以适配安装器的空离线缓存。

[桌面载体决策](../architecture/2026-08-20-tauri-desktop-carrier.zh.md)仍负责原生过滤、通用通知内容、系统权限和传输。此策略不取代该职责或 [Focus Timer 决策](2026-09-07-focus-timer-bundle.zh.md)；两个可选 Bundle 分别验证独立的 UI 与任务行为贡献。

## 考虑过的替代方案

**由第二个插件发送通知。** 不采用，因为原生提供方已经观察符合条件的轮次并负责送达。策略扩展保留单一发送方与现有默认行为。

**将开关放进市场或原生宿主。** 不采用，因为可选 Bundle 必须拥有自身的设置和可撤销行为。市场提供安装与扩展 slot，Rust 保留操作系统集成职责。

**修改 agent loop 或 Session 格式。** 不采用，因为通知送达属于提交后的桌面职责，不贡献任何模型可见输入。

## 影响

Bundle 改变通知策略，不替换 Harness 执行或原生恢复。受信任的同进程插件仍可直接调用通知 API；此策略不是安全沙箱，也不限制所有可能的发送方。原生前台抑制与系统授权仍独立生效。

单元测试覆盖默认值、独立开关、策略委托与 dispose（资源释放）、写入失败和策略异常。打包验收使用固定版本 pnpm 和空离线缓存安装真实审核产物，操作实际浏览器界面，通过原生提供方发出 Session 事件，重启验证持久化，再移除 Bundle 验证默认行为恢复。经过认证的原生桥接使用 fixture（测试前置数据）；真实系统通知送达仍需目标平台验收。
